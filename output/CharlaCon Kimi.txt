OpenCode optimiza
El problema está casi seguro en el input (lo que tu app envía al modelo), no en el output. En arneses de codificación, el input suele representar 80–95% del consumo total de tokens. El output del modelo es solo el texto que genera; el input es todo lo que tú le envías: system prompt, historial de la conversación, descripciones de herramientas, contenido de archivos y resultados de comandos.
Aquí te dejo un mapa de dónde buscar, ordenado de más probable a menos probable:
1. Salidas de comandos sin truncar (el culpable #1)
Cuando tu app ejecuta grep, cat, ls -R, find, etc., y envía la salida completa al modelo, eso puede ser miles de tokens de golpe. OpenCode trunca agresivamente:
Hojas
Lo que hace tu app (probable)	Lo que hace OpenCode
Envía los 500 resultados de grep completos	Trunca a las primeras 20 líneas relevantes
Envía un archivo de 300 líneas entero	Envía solo los 50 tokens alrededor del match
Envía ls -R de un proyecto grande	Filtra por extensión o usa glob con patrón
Revisa: Después de ejecutar un comando en tu app, ¿cuántos caracteres/texto envías al modelo? Si es más de ~2.000 caracteres por comando, ahí está gran parte del problema.
2. Historial de conversación sin compaction
Si tu app mantiene todo el historial de mensajes (user → assistant → user → assistant…) desde el inicio de la sesión, el contexto crece exponencialmente. Cada vuelta incluye no solo el nuevo prompt, sino todo lo anterior.
OpenCode hace:
Compaction automática cuando se acerca al límite de contexto.
Comandos como /drop para eliminar archivos del contexto.
Uso de small_model para tareas de resumen.
Revisa: ¿Tu app recuerda toda la conversación desde el inicio? ¿Cuántos mensajes hay en el array messages que envías a OpenRouter?
3. Descripciones de herramientas (function calling) infladas
Si usas function calling / tools, cada herramienta que defines en el system prompt consume tokens en cada llamada. OpenCode usa plugins como OpenSlimedit que comprimen las descripciones de herramientas y las salidas de archivos, logrando reducciones del 11–45%.
Revisa: ¿Cuántas herramientas defines? ¿Cuán largas son sus descripciones? ¿Las envías en cada request o las mantienes en el system prompt? OpenCode incluso permite definir un small_model para tareas simples, ahorrando tokens del modelo grande.
4. Contexto de archivos redundante
Cuando tu app lee archivos para "entender el proyecto", ¿los reenvía enteros en cada prompt? OpenCode:
Usa grep y glob para leer solo lo necesario.
Permite al usuario hacer /drop para quitar archivos del contexto.
Tiene un límite consciente de cuánto contexto mantiene activo.
Revisa: ¿Tu app reenvía el mismo contenido de archivo en cada mensaje nuevo? Eso es duplicar tokens innecesariamente.
5. System prompt largo o ineficiente
Un system prompt detallado es útil, pero si excedes los 500–1.000 tokens solo en instrucciones base, estás pagando eso en cada request.
Revisa: ¿Cuántos tokens tiene tu system prompt? Puedes contarlos aproximadamente: en inglés, ~1 token ≈ 0.75 palabras.
6. Formato de los mensajes
OpenCode optimiza el formato de sus mensajes (probablemente usa un formato compacto para las herramientas). Si tu app envía JSON muy verboso, Markdown excesivo, o repite metadatos innecesarios, eso suma.

OpenRouter no añade
OpenRouter no manda ningún system prompt. Es solo un proxy: recibe tu JSON y lo pasa tal cual al modelo final. El system prompt que llega al modelo es exclusivamente el que envía tu app (o el que envía OpenCode).
¿Quién manda el system prompt?
Hojas
Quién	Qué envía
Tu app	Tu system prompt personalizado + user prompt + resultados de herramientas
OpenCode	El system prompt interno de OpenCode (optimizado, compacto) + user prompt + resultados truncados
OpenRouter	Nada. Solo reenvía lo que le mandes. No añade instrucciones, no modifica el system prompt.
OpenRouter no es como un "intermediario que añade su propia voz". Es un pasamanos técnico. 
¿Tu app siempre gastará más por culpa de OpenRouter?
No. OpenRouter no suma tokens a tu system prompt. Si tu app gasta el doble, es porque tu app está enviando más contenido, no porque OpenRouter añada algo.
La comparación real es:
plain
Tu app input  ≈  [Tu system prompt grande] + [Archivos completos] + [Salidas de comandos largas]
OpenCode input ≈  [System prompt compacto] + [Fragmentos de archivos] + [Salidas truncadas]
Entonces, ¿por qué OpenCode gasta la mitad?
Porque el system prompt de OpenCode está diseñado para ser eficiente:
Sin ejemplos few-shot: No gasta tokens en ejemplos de "cómo responder".
Descripciones de herramientas comprimidas: Usan lenguaje técnico conciso.
Sin inyección automática de contexto: No envía el árbol de directorios ni resúmenes del proyecto a menos que se los pidas explícitamente.
Tu app, en cambio, probablemente está enviando un system prompt de 3.000–8.000 tokens (con ejemplos, personalidad, reglas, descripciones de herramientas extensas) mientras que el de OpenCode ronda los 1.000–1.500 tokens.
Resumen
Hojas
Pregunta	Respuesta
¿OpenRouter añade system prompt?	No.
¿Por qué mi app gasta más?	Porque tu app envía más input (system prompt largo + archivos completos + salidas sin truncar).
¿Es culpa de OpenRouter?	No. El culpable es la arquitectura de tu app.
